## D. Loss payout — decision for architect/coordinator

**Current implementation exists:** `HeatPayout.missStars(false, goalsMet)` pays flat **2 Stars when at least one goal was met**, on every heat; zero goals pays 0. It is already inside the idempotent award transaction and subject to existing pass/supporter treatment. Thus “losing always pays nothing” would be an incorrect diagnosis.

**Recommended small extension for the new QA request:** keep the existing +2 partial-goal award; add **+1** for a genuinely completed lost field with no goal but **score ≥100, ≥3 server-counted merges, and ≥6 accepted drops**. Zero input/quit/reset/restart never earns finish Stars. Wins and clean bonuses stay unchanged. This rewards visible effort while keeping full goals worthwhile; it is an initial tuning default, not a measured economy projection. If coordinator prefers no economy retune yet, ship truthful existing +2 results/copy and record the new score floor separately rather than silently inventing a change.

Implementation if accepted: pure `missStars` accepts validated run summary; compute from the immutable saved candidate inside `Hatching.award`; preserve existing `missPay` receipt field/idempotent lastAwardSeq, v11 optional compatibility and old two-argument behavior.
