## Existing contracts and constraints

- `MaterialCatalog`: CatalogVersion1, active PoolVersion2 `{gloss,matte}`,16Stars, no-duplicate equal odds; historical pools1–3 remain immutable. Metal is a legacy finish. Pearl/Speckle are unshipped data. Jelly must never enter PaidOrder/Pools/remaining/odds/fixedNext.
- `MaterialState` stores permanent `materialUnlocks`, per-owned-pet `petMaterials`, bounded32 exact operation receipts, and optional pending Material Egg result/reservation. `HatchProgress.materialCommand` uses the existing fenced root transaction and durable proof/retry path. All current v11 validators call MaterialState.valid; no save version bump or inventory bit is needed.
- `PetAppearance.public` already replicates each saved per-pet finish. `PetMaterials` binds verified native profiles; `PetMaterialConfig` selects one/two-tone profiles. `GardenPetVisual` is the sole final part-visibility owner: hidden expressions/accessories become1; otherwise authored base transparency. `PetNightSurfaces` supplies the bounded fallback. Every view using PetFactory inherits this renderer; no hatch production changes are needed.
- BodyTwoTone ColorMap alpha already means primary/secondary blending in **Overlay** mode. Switching that map to Transparency would destroy its pigment meaning. Roblox documents Overlay vs Transparency as distinct alpha semantics: [AlphaMode](https://create.roblox.com/docs/reference/engine/enums/AlphaMode), [PBR textures](https://create.roblox.com/docs/art/modeling/surface-appearance), [BasePart](https://create.roblox.com/docs/reference/engine/classes/BasePart). Native tests, rather than API metadata, must establish the combined translucent-PBR result.

## Transaction / compatibility edge cases

Same id+quote after ambiguous accepted write must return existing committed receipt even if requirements no longer appear to hold; conflicting quote same id rejects. Before-write failure retries same operation without reward. Concurrent clients share existing account fence; only the winner commits; other current state shows owned. Bond4 rejects, exact5 accepts, unowned pet bond5 rejects; Gloss-only/Matte-only reject. Claim never consumes Stars, fruit, bond or other entitlements; no autoequip. Revision change rejects stale new command; existing exact proof remains accepted. Pending egg/reveal blocks claim without clearing it. EquipJelly still checks owned pet, earned entitlement and expectedFinish; Standard affects finish only, Original colour affects Hue only. Receipt eviction must leave unlock valid and stale replay harmless. Existing future/rollback bond sanitization remains unchanged.

Old v11 saves with no Jelly load byte-compatible; new optional known unlock/receipt uses existing fields. **Older running server code cannot validate a new known finish ID**: rollout must replace/drain old servers before exposing claim, using the coordinator's existing stale-server gate. Do not claim mixed-version compatibility or publish automatically. If that gate cannot be guaranteed, keep claim disabled until a separately reviewed forward-compatible migration is agreed.
