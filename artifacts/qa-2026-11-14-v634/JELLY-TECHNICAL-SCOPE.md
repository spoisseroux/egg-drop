# Jelly technical scope — read-only source review

No Jelly material, catalogue, save or runtime code has been changed. `JELLY-FINISH-SCOPE.md` owns creative direction; its milestone and opacity numbers remain recommendations. Preview/native proof precedes implementation.

## Rendering seam

- `src/client/PetMaterials.lua:11-18` protects authored textured parts and selects body/secondary finish surfaces. `:65-87` picks a verified finish and two-tone variant. Add a distinct Jelly profile only after actual native validation; preserve the original tint and body/secondary gradient. Existing surface alpha is **Overlay pigment blending**, not proof of translucency (`:83-84`, `scripts/BuildPetMaterialTemplates.lua:29-31`). Replacing the two-tone gradient alpha with transparency would lose the established colour treatment.
- `src/client/GardenPetVisual.lua:400-410` resolves expression/hidden state and writes final `Transparency` each pose. A separate loop assigning `.22` would reveal hidden mouths/glints, fight the existing writer, and fail to restore Standard cleanly. Add one explicit finish-opacity contribution at this final visibility seam: hidden stays 1; visible base opacity composes with finish opacity. Identify eligible pigment parts through the actual definition roles and explicit face/accessory exclusions; do not infer from every descendant or blanket the whole model.
- `src/client/PetMaterials.lua:113-116` already suppresses emission for hidden forms; `src/client/PetNightSurfaces.lua:13-35` owns bounded fallback fill/reparenting. Preserve those owners, existing facial shading and charm visibility. Eye/mouth/nose/white/glint parts, wearables and charms stay opaque. Switching finish must clear only Jelly's contribution, retain authored base transparency and never reset Hue. Review both authored and primitive fallbacks explicitly.
- Blender cannot prove Roblox partial-transparency sorting. Before any acceptance, test actual Standard / Gloss / Metal / Jelly at identical light/camera, front/three-quarter/full/phone, golden Bear and Rose/Tide, day/night, stripe background, accessory + charm, blink/mouth swaps and all entry points (garden/portrait/reveal/visitor). Metal is an existing **unverified non-sellable candidate**, not a gold finish (`assets/pet-materials/manifest.json:146-153`). Start 22%/12%, inspect far-eye/internal intersections/shadow, then 15% if necessary. Native outcome may require revising the resin approach.

## Entitlement seam, only if milestone is approved

- `src/shared/MaterialCatalog.lua:10-15` already separates known finishes from the immutable paid pools. Add Jelly to known/equippable finish data while leaving `PaidOrder`, PoolVersion 2, historical pools and 16-Star Gloss/Matte odds unchanged. Do not activate pool 3 Pearl/Speckle. Hue remains its four outcomes / 8 Stars.
- `src/server/MaterialState.lua:61-69` validates every saved unlock/equip/receipt against catalogue IDs; `:107-132` performs typed purchase/ack/equip mutation. A free milestone needs an explicit typed claim action and cost-zero receipt/proof branch, not a naked unlock or a pretend `materialBuy`. Validate Gloss + Matte ownership and **an owned pet's saved bond XP** inside the same fenced save transaction. `src/shared/BondCatalog.lua:19,50-55` currently makes level 5 equal 250 XP; call the shared level function rather than duplicate that number. `src/server/BondState.lua:38-49,66-79` handles missing/valid saved XP.
- Reuse `src/server/HatchProgress.lua:443,659-685` operation IDs, revisions, retry/proof handling; bind claim to a stable milestone ID, no wallet decrement, one permanent Jelly unlock. Duplicate/concurrent/rejoin claims return saved proof. Eligibility and receipt UI must use confirmed public state (`MaterialState.lua:138-139`, `src/server/PetAppearance.lua:29-40`), with accurate unmet requirements and no random/pity wording. Existing pending paid receipts/reservations remain resumable and cannot be consumed by the new claim.
- New ID acceptance can fit the existing additive maps in current v11, but **rollback compatibility is a real gate**: an older build's strict `Catalog.known` validator rejects a save containing Jelly. Define a compatible rollback/release plan before enabling claims; do not silently discard unknown finish ownership. No source evidence justifies claiming old executables can read the new ID unchanged.
