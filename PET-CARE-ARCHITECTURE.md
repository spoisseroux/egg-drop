# Pet-care expansion: implementation constraints

Planning review only, November 9, 2026. Runtime remains private v316 / c549451; no expansion code or assets are released. Read the creative/interaction proposal in [PET-CARE-EXPANSION.md](PET-CARE-EXPANSION.md). Astra owns visuals and behavior design; Sol 6.1 High implements separately reviewed slices. Independent Sol inspected the current source to identify these boundaries.

## Save data and six pigments

HueCatalog currently has four explicit pigment keys, fifteen nonempty subset anchors and a five-result item roll including Reset. HueState v6 validates exact vectors, inventory, reservations, receipts and catalog versions. Adding keys directly would invalidate existing records.

Introduce a versioned successor with frozen historical validators and catalog tables. Zero-pad only the current working state; preserve every old receipt, pending roll, quote, token proof and paid preset under its original version. Reconcile old reservations before creating a new-price/new-pool operation. Cover load, retry, renewal, release, takeover and rejoin, not just the first migration. Preserve the entire old four-color numerical subspace. New mixed-color layers need a defined resolver for all six pigments; six pigments have63 nonempty subsets and46,656 legal five-dose vectors per channel. Rendering and UI swatches call one resolver. Ink is a real item indicated by counts, never inferred as Reset from a dark RGB value.

New feature/stat/finish items need a typed inventory namespace and versioned exact operations rather than arbitrary keys added inside the old hue inventory. Eggs retain the server roll → durable reservation → atomic Stars debit/stock/receipt → reveal sequence. Item application atomically targets one owned stable pet and consumes one stack. Repeated, conflicted, capped or canceled requests cannot spend twice or reroll. Receipt compaction must retain referenced pending proofs. Target protection, prices and actual chances belong in the pre-purchase quote. A displayed rare chance must include the current guaranteed state. Companion misses, Hue-target misses and Feature-target misses are three independent namespaces. A reservation captures its target, counter state, quoted pool/version and guaranteed state. Advance/reset that counter once in the durable purchase transaction, never on reveal or acknowledgement; neither new counter can change the frozen Companion counter.

Keep all seven permanent IDs/ownership bits and the separate four-active hatch set. Existing owned retired pets remain valid targets. Per-pet feature stages, finish selection and training XP are separate from hue counts and frozen historical Family Mastery. Reset Hue cannot clear another system. Canonical training data is total integer XP per stable pet/stat plus a curve version. Derive level and XP-to-next; any stored level is only a validated cache. Preserve earned total XP when extending curves. Never trust a client-supplied level or traveled distance for rewards. Account-wide finish unlocks can be equipped independently per pet.

## Rendering and loading

Current GardenPetVisual checks mesh IDs, resource sizes and the presence of all required parts before building an authored rig. That proves metadata, not downloaded geometry. Preserve its synchronous Factory callers: prepare a complete semantic native fallback, preload the actual required MeshPart instances in bounded batches, then replace the whole visual with a generation fence. Root/expression, bounds, prompt references and selected features must change together. A timeout or denied head keeps a complete fallback. Never refund or reroll a committed item because a render failed.

The material experiment is parked in stash7f72106e5d3a9444c6ae4b03be975f637e2c0505. Keep its native findings: raw-URI callbacks failed; parented image-instance loading succeeded; unparented IsLoaded remained false despite successful fetch callbacks. No such probe proves processed SurfaceAppearance rendering. Finishes require actual normal-client, low-graphics and preview checks. The first two original meshes lack UVs, so an anatomical gradient requires an authored UV update or a visibly stepped fallback. A UV refresh alone does not solve hue-to-white compositing under multiplicative tint: require an actual endpoint/compositor proof or an explicitly accepted stepped fallback before offering that gradient. Author immutable material maps in Edit, clone prepared profiles, and change only supported tint/emission controls at runtime. SurfaceAppearance is device/quality dependent. [Roblox SurfaceAppearance](https://create.roblox.com/docs/reference/engine/classes/SurfaceAppearance) · [ContentProvider](https://create.roblox.com/docs/reference/engine/classes/ContentProvider).

Feature growth changes attachment bounds, pose and cache keys. Test stage5 horns with a visible charm, both wings while held, face clearance and simultaneous features on all seven rigs. Cosmetic wings do not grant training or flight. Keep eye/glint/closed-mouth contrast on Ink coats and distinguish body glow from charm glow. Coos and item effects have shared crowd budgets, mute/reduced-motion handling and no progression authority.

## Carry, machine and water

GardenState currently has one actor per owner with Room/Board/Focus behavior; owner movement cancels several non-follow actions. Add explicit Carried, Docked and Placed transitions rather than overriding the existing follow pose. A server-owned descriptor ties the pet to owner, character generation and actor generation; clients render a cosmetic attachment. There is no need for a network-owned physics pet. Support both R6/R15 carry poses. Release existing toy/rest/greeting reservations before a hold. Validate reach, station reservation and supported placement with pet-sized clearance; do not persist arbitrary world CFrames.

A one-bay prototype needs an exact generation-bound claim and expiry. Pet switching must replace that owner's single actor atomically, with the old pet preserved until save succeeds. If a bay expires before an equip response arrives, an already committed equip remains saved truth: resume ordinary follow with that pet, never roll it back or reclaim another owner's bay. Only an uncommitted failure keeps the previous equipped pet. Death, disconnect, mode interruption and an old late release cannot duplicate a pet, evict another occupant or strand an attachment. Rejoin restores the saved equipped pet in ordinary follow. Keep menu shortcuts while the physical path is proven; machine-only editing is a product decision, not a necessary technical restriction.

Pets are cosmetic models without Humanoids. The current water is decorative Parts excluded by dry path planning. Automatic Humanoid swimming is not their swimming system. Add registered water surfaces, shallow/deep regions, safe shoreline entries/exits and a dedicated crawl/walk/paddle/tread/swim state owner. Beginners can practice safely; dry access to essential stations remains available. Carrying/docking and swimming cannot own the same pose simultaneously. Basic following comfort must not collapse at low Movement levels. [Humanoid reference](https://create.roblox.com/docs/reference/engine/classes/Humanoid).

Use original tileable water/waterfall textures and a shared bounded animation update, with reduced-motion stills. Texture offsets can provide scrolling on registered surfaces; physical wet zones remain independent of texture placement. The supplied Sonic OBJ/PNGs are local reference material and are not imported or uploaded into the game. Its sky-shell bounding box does not describe playable scale. [Texture controls](https://create.roblox.com/docs/reference/engine/classes/Texture).

## Handheld and release gates

Trigger merge feedback from an accepted merge serial, not every render frame. Scale/cap a short device-art shake by tier and chain burst; reset on mode/overlay/teardown and replace motion with a local flash when reduced motion is selected. Keep hit targets and aim coordinates stable. Increase motif transparency slightly over an opaque theme base so the old world-bleed bug does not return.

Every slice needs independent source review, native controls where possible, isolated transaction/lease/receipt tests, all-seven visual compatibility and honest device evidence before private publication. Carry/machine additionally needs two-owner contention and interruption tests. Swim/stat items cannot release before their advertised behavior and one purposeful practice activity work. Physical-phone performance, live-service save/rejoin and longer human play remain separate outstanding tests. There is no new currency, paid luck, nursery, battle system or public release in this plan.
