## 2. LCD surface and fixed-light jelly

The existing `JellyLCD` has one 84 × 112 buffer, a 30 Hz write cap, palette rasterization and `ResampleMode.Pixelated`. Its ellipse distance and lighting both currently use local rotated coordinates. `JellySprite` creates a procedural GUI body, gradient and glints. Its parent rotation turns all three with the impact axis. The private baseline uses that GUI fallback. An apparent revolving painted highlight can therefore come from the transform even though this path loads no jelly PNG. `JellyVisual` is a Studio mesh preview.

1. **Fix the material in both paths.** Use screen upper-left as the shared light direction. Retain the existing squash, rebound, floor squeeze, center and collision motion. In `JellyLCD.draw`, compute inside/edge distance with the rotated ellipse, then evaluate the shading coordinate in tray space. Bound and normalize it using the deformed extent. Keep a continuous deep rim, body color, smaller upper-left highlight and calm lower-right shade. The merge surface uses the same light convention. In `JellySprite`, keep the highlight centered on the upper-left screen quadrant and inside the deformed silhouette through bank impacts. An independent light layer positioned from the deformed bounds, or a correct inverse transform for both position and orientation, accomplishes this. Counterrotating the gradient alone leaves the glint orbiting. Keep tier text separately positioned and upright.
2. **Prototype a real LCD fallback first.** Derive the logical height from the projected board aspect once, as `round(84 × (Config.Height + 0.8) / (Config.Width + 0.8))`. At today's 11.8 × 19.8 board this gives **84 × 141** cells. The old 84 × 112 grid stretches round pieces vertically by about 26% when the same scalar radius is used in both axes. The new grid preserves square display cells to within 0.04%, so rotating an ellipse, blending a merge or drawing a sloped bank uses one distance metric. Compare the projected outlines of a stationary circle, two touching neighbors and elongated ±45°/90° impacts with their expected screen bounds to within one cell. Reuse the distance/material samples and 30 Hz owner. Keep `CreateEditableImage` as the fast backend where permitted. In the published-compatible fallback, draw the static board once and compose dynamic pixels into horizontal spans of one palette color. Use pooled borderless Frames aligned to the same grid, optionally coalesce identical vertical spans. Keep physics positions continuous. Give every logical pixel the same screen-edge rounding convention so adjacent spans have no cracks at fractional magnification. Reuse or hide stale spans after merges/resize, cache unchanged rows/rectangles, and keep glyphs in a separate readable layer. Avoid one GUI Instance per pixel or a second simulation/render clock.

   Benchmark this backend *before* polishing it. The larger grid has 26% more sample cells. Record the baseline and candidate on the same Studio device profile for idle, falling, long 24-drop pile and multi-piece merge. Record allocated/alive/visible span counts, peak property writes per frame and p50/p95 client render cost/frametime. If a lower-height grid is necessary, convert samples into common projected distance units before all ellipse rotations, merge/capsule distances and sloped bank calculations. Set a hard pool cap from the measurements; exercise overflow and sustained pressure with a deterministic crowded board. The fallback must have capped work, recover without oscillating between backends, avoid per-frame Instance creation after warm-up, stop drawing when covered/hidden, and release resources on teardown. Keep a cheap procedural gel fallback if memory or timings exceed the cap. Give this last path quantized visual positions, stepped silhouette/highlight shapes and a sparse static tray texture. Report its reduced pixel treatment explicitly if it has to be the default. A scanline overlay alone cannot reproduce low-resolution pieces. No new private place setting is required.
3. **Use bounded Roblox rendering.** The root verified gradient Type/Scale/TileMode in this Studio. Try Radial or Elliptical at creation time if supported, with a short color ramp and linear alternative. Select the path once. Continue to accept nil allocation and runtime write failure from the optional LCD. After failure, every piece and its mark must be visible in the GUI path on the next frame. Roblox exposes fixed light parameters on ViewportFrame and buffer writes on EditableImage. This pass specifies the visible result using these APIs. [UIGradient](https://create.roblox.com/docs/reference/engine/classes/UIGradient) · [EditableImage](https://create.roblox.com/docs/reference/engine/classes/EditableImage) · [ViewportFrame](https://create.roblox.com/docs/reference/engine/classes/ViewportFrame)

**Gate.** Photograph the same tier before impact, during a sideways squash and at rest under one upper-left light. Verify the shape deforms while the glint stays on the light side. Test actual private-compatible GUI fallback, the permitted LCD path if available, deliberate fallback, reduced effects, merges, cross-tier marks and resize. A static or synthetic three-angle comparison proves orientation, while actual drops prove visibility and input. Compare frame work and instance count against baseline with a populated tray, and after repeated board/room transitions. Label evidence by renderer and distinguish measured performance from visual judgement.

**Measured candidate.** After benchmarking the 84 × 141 prototype above, use **64 × 107**, still derived from the board aspect, with a 1,536 dynamic-span cap. In the matched Studio benchmark, 24 falling pieces took 4.983 ms at p95 for a paint frame, down from 7.297 ms at 84 × 141. Multi-merge took 3.455 ms, down from 5.054 ms. Peak observed demand was 895 spans. In a 172 × 289 display fixture the smaller blue piece retained a distinct body and dark rim, while larger pieces retained their diagonal and vertical silhouettes. This accepts the proposed shape resolution and cap. Fixed lighting, tier marks, production failure recovery and gameplay are separate gates.
